# Слияние checker + anti-raid бота

Оба бота теперь один процесс, один токен (`BOT_TOKEN`), один вебхук. Сервис
проверки подписок (бывший отдельный checker) встроен как модуль `checker_core.py`
и доступен по HTTP на том же сервере, на путях `/checker/*`.

## Что изменилось

- **bot.py** — единая точка входа: один `Bot`, один `Dispatcher` со всеми роутерами
  (anti-raid + `checker_core.router` + `chat_captcha.router`), один aiohttp-сервер
  (вебхук + HTTP API checker'а), один `set_webhook`. Отдельного polling для checker'а
  больше нет — его команда `/set`, коллбек `set:...` и обработчик `chat_member`
  работают через тот же вебхук, что и весь остальной бот.
- **checker_core.py** — бывший `main.py` из checker, без FastAPI/uvicorn: HTTP-эндпоинты
  переписаны на `aiohttp.web.RouteTableDef` (`routes`), логика проверки подписок,
  фоновые воркеры (`log_sender_worker`, `error_summary_worker`, `cleanup_worker`) —
  без изменений по сути.
- **topics.py** — новый модуль: создаёт темы (`createForumTopic`) прямо в личке
  владельца с ботом (Bot API теперь это поддерживает без отдельной группы-форума).
- **db.py** — добавлена таблица `topic_mappings` (kind="bot"/"channel", key, thread_id) —
  чтобы темы переживали рестарт и не создавались заново.
- **logic.py: notify_admins()** — теперь принимает `chat_id`/`chat_title`; если они
  переданы, лог уходит в тему этого чата у владельца (создаётся автоматически при
  первом таком событии).
- Во всех местах anti-raid части, где было `logic.notify_admins(bot, text)` и рядом
  есть `chat_id` (вступление/выход из чата, бан по CAS, флуд-мьют, рейд/экстренный
  бан) — теперь передаётся `chat_id=..., chat_title=...`, чтобы лог шёл в тему
  нужного канала/группы, а не общим потоком.

## Как это ведёт себя в проде

1. **Тема на бота.** Как только какой-то клиент-бот (bot_name) впервые обращается
   к `/checker/check` или `/checker/check_many` — для него создаётся тема
   `🤖 <bot_name>` в личке владельца, туда падает одно сообщение "бот
   зарегистрирован". Сами результаты проверок подписки в эту тему НЕ идут (см. п.2) —
   тема бота нужна для факта регистрации и общих логов, не привязанных к каналу
   (например, сводка ошибок раз в `CHECKER_ERROR_SUMMARY_INTERVAL`).
2. **Тема на канал/группу.** И у checker'а (результаты `/check`, `/check_many`,
   восстановление после сбоя), и у anti-raid части (вступление, выход, бан по CAS,
   флуд-мьют, авто-рейд, экстренный бан) для одного и того же `chat_id` используется
   ОДНА И ТА ЖЕ тема `📢 <название канала/группы>` — она создаётся автоматически при
   первом относящемся к этому чату событии.
3. Если ADMIN_IDS содержит несколько ID — темы работают только для владельца
   (`TOPICS_OWNER_ID`, по умолчанию — наименьший ID из ADMIN_IDS). Остальным админам
   те же логи по-прежнему приходят, но одним потоком, без тем (Bot API поддерживает
   темы только в приватном чате конкретного пользователя, "общих" тем на несколько
   разных ЛС не бывает).

## Веб-капча (Mini App) убрана — теперь капча прямо в чате

Раньше капча открывалась через Telegram Mini App (веб-страница в `webapp/`). Сейчас
это убрано (см. `chat_captcha.py`) и заменено на капчу прямо в переписке: пользователю
показывается видео (`assets/chat.mp4`) с подписью `CAPCHA: Составь фразу: «Я принимаю
правила чата»` и 4 кнопками — по одной на каждое слово. У каждой кнопки 4 варианта
слова (правильный + 3 отвлекающих), клик листает вариант по кругу; когда все 4
кнопки показывают правильное слово по порядку — проверка пройдена. На это даётся
`CAPTCHA_TIMEOUT_SECONDS` (по умолчанию 90 сек), иначе — кик/отказ (можно зайти
заново).

Механика одинаковая во всех трёх сценариях, отличается только что происходит при
успехе/провале:
- **Вступление в группу** (`handlers/joins.py`) — капча прямо в группе; при успехе
  снимается ограничение и шлётся приветствие; при таймауте — кик.
- **Личная ссылка на канал** (`handlers/start.py`, кнопка «Ссылка для входа через
  бота» в карточке чата) — капча в личке с ботом; при успехе бот выдаёт одноразовую
  ссылку-приглашение.
- **Заявка на вступление в канал** (`handlers/requests.py`, режим подтверждения
  заявок) — капча в личке с ботом; при успехе заявка одобряется автоматически.

Удалены: `verification.py` (весь механизм токенов/валидации `initData` для Mini
App), папка `webapp/` (HTML/JS/CSS страницы капчи), эндпоинты `/api/challenge` и
`/api/verify` из `server.py`. `server.py` теперь — голый aiohttp-app, на который
вешаются только вебхук бота и HTTP API checker'а.

## Обязательно перед запуском

1. В `@BotFather` → выбрать бота → **Bot Settings** → найти пункт про темы
   (Topics/Direct Messages) в приватных чатах — включить. Без этого `createForumTopic`
   будет возвращать ошибку, и бот тихо откатится на логи без тем (в консоль один раз
   упадёт предупреждение — см. `topics.py`).
2. Владелец (`TOPICS_OWNER_ID`) должен хотя бы раз написать боту в личку — Telegram
   не позволяет боту первым создать тему в чате, в который он ещё не заходил.
3. Заполнить `.env` по `.env.example` — добавлены `TOPICS_OWNER_ID`,
   `CHECKER_API_KEY`, `CHECKER_REDIS_URL` (опционально) и остальные `CHECKER_*`.
4. `pip install -r requirements.txt` (FastAPI/uvicorn больше не нужны, добавлен `redis`
   как опциональная зависимость — без `CHECKER_REDIS_URL` состояние checker'а живёт
   в памяти процесса).

## Клиентские боты (которые проверяют подписку через этот сервис)

`client_example.py` обновлён под новые пути: `POST/GET {WEBAPP_URL}/checker/check`
и `{WEBAPP_URL}/checker/check_many` (было `{CHECKER_URL}/check`). Заголовок
`X-API-Key` и остальной контракт — без изменений.

## Что НЕ трогалось

Вся админ-панель (`dashboard.py`), антифлуд, эвристики, CAS, экстренный авто-бан —
логика оставлена как есть, только `notify_admins` в местах, привязанных к
конкретному чату, стала передавать `chat_id` для маршрутизации по темам.
